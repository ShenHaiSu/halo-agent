# 00 现状诊断与问题清单：现有会话渲染链路到底烂在哪

> 基线：`develop/src/Web.Client` + `develop/src/Host.Desktop/Services/Projection` + `AgentOrchestrator.cs`。
> 设计对照：`docs/learnDocs/zcodeDocs/04/05/06`。
> 本篇所有“证据”均可在基线仓库按文件+关键词复核，不依赖猜测。

## 1. 数据链路总览（现状实测）

```text
LLM SSE/HTTP
  -> AgentOrchestrator.RunAgentTurn 循环
      |-- PublishStreamDelta(TextDelta/ReasoningDelta) -> JsEventDispatcher -> haloEventBus llm:stream-event
      |       -> agentStore.streamingText += delta / streamingReasoning += delta   [瞬态桶A]
      |-- PublishTurnEvent(ToolCallStarted/Updated/Args/Completed/ExecutionStarted/Completed/...)
      |       -> agentStore.toolCards[] 增量拼装                                [瞬态桶B]
      |       -> RowProjectionStore.OnTurnEvent/OnStreamDelta -> StreamToRowProjector -> DeltaLog [投影C]
      |-- 持久化 messages.jsonl -> workspaceStore.sessionMessages                 [持久D]
              -> MessageTimeline 持久区渲染 (buildTurnGroups + buildTimelineEntries)
              -> projectionStore.snapshotFromMessages(D) 重建快照行 (rowIdSeed 自增)

渲染 = D(持久) + A/B(流式容器 active-turn-container) + C(只读对账 refreshFromProjection)
```

对照 `zcodeDocs` 的理想链路 `统一事件 -> 行增量 -> snapshot/delta帧 -> TurnUnit -> 行分发`，现状是**三源并存 + 双容器 + 单向对账 hack**：

| 理想（zcode） | 现状（halo-agent） | 差距定级 |
|---|---|---|
| 唯一真相源 = 投影行 | 持久真相=D，流式真相=A/B，投影C只做“修正卡的 argsJson/状态” | P0 致命 |
| 行 `rowId` 后端单调分配永不复用 | 前端 `snapshotFromMessages` 用模块级 `rowIdSeed++`，每次 `loadSessionMessages` 全量重编 `rowId` | P0 致命 |
| 轮内 `assistantWorkRows` 保序 | `TurnGroup{content, reasoning, toolMessages}` 三桶，`content` 单字符串合并，顺序丢失 | P0 致命 |
| 文本追加 `row.delta` + 状态 `row.upserted` | 持久区无增量（全量重算 `buildTurnGroups`），流式区字符串 `+=` 直接触发全量 `md.render` | P0 性能 |
| 工具组 + 折叠舱 | 工具逐卡平铺 + “思考与工具”单舱全收/全展，burst 10 连击占满首屏 | P1 体验 |
| `output.text` 流式（终端直播） | 只有 `inputText` 流式（且 P1-F2 后流式区已不再拼 `args`，工具流式期显示空参数），`output` 只在 `ToolExecutionCompleted` 一次性到达 | P1 功能缺失 |
| 虚拟列表 + 引用共享 | 仅 `turnWindowSize=30` 截断 + `v-memo[content]`，窗口内仍全量挂载 diff/图片/高亮 | P1 性能 |

## 2. 前端渲染现状逐文件诊断

### 2.1 `MessageTimeline.vue`（652 行，最大病灶）

- **双容器并存**：`timelineItems`（持久 D，L235-259）+ `active-turn-container`（流式 A/B，L111-141）。轮末 `finishTurn` 清空流式容器、依赖 `loadSessionMessages` 全量重拉对账，中间有 1 帧“双影/空洞”（`lastTurnSnapshot` 事件只发不收，`agentStore.ts L690-693` 发射 `agent:turn-archived` 但 `MessageTimeline` 无订阅）。
- **三桶合并丢序**：`buildTurnGroups`（`turnGroup.ts L168-331`）把 `assistant.content` 合并为单字符串、`reasoning` 合并为单字符串、`toolMessages` 为列表。`正文→工具→正文→工具`（多 response / 多 iteration 同用户轮）在持久化后变成“多 `TurnGroup`”或“单组单 `content` + N 工具”，模板 L52-97 渲染为“正文常显 + 思考与工具合舱”，因果链断裂。例：模型先说“先查 A”，调 `grep`，再说“再看 B”，调 `read_file` —— 现状显示为两段正文被拼进不同 `TurnGroup` 或同一 `content`，工具全部堆进同一折叠舱，无法逐段对照。
- **`v-memo` 误用**：`v-memo="[String(item.group?.content)]"`（L56）只对字符串判等，但 `content` 是合并后大字符串，流式期持久区不更新所以无意义；流式区 `agentStore.streamingText` 变化直接触发 `MarkdownStream.text` 全量重渲染，无节流。
- **Markdown 双模**：`useMarkdownStream` 默认开（L333），但关闭时回退 `v-html="renderMarkdown(...)"`（L71），两套渲染函数（`MarkdownStream.vue` 内 `md` 实例 + 本文件 L396 `md` 实例）行为不一致（容错规则不同），终态可能闪变。
- **思考+工具合舱**：L75 单舱 `turn-thinking-tools`，头行 `🧠 思考与工具调用 · N 个工具`，`expandedTurns` 默认全收（L220）。问题：① 思考（token 流）与工具（状态机）两种心智模型被迫共用一个折叠；② 舱内 `max-h-72 overflow-y-auto` 嵌套滚动 + 外层时间轴滚动，双滚动打架；③ `reasoning` 用 `whitespace-pre-wrap` 纯文本（L89），长思考无 Markdown、无计数、无耗时。
- **工具逐卡平铺**：L91-94 `v-for t in toolMessages`，每工具一 `ToolCallCard`，`key=messageKeyOf(id, toolKey)`。连续 10 个 `grep`/`read` 直接 10 张卡，无分组、无汇总、无批量折叠。`hiddenToolCallIds`（`agentStore L238`）靠流式卡 `callId` 集合隐藏持久侧同 `callId` 灰块，属于“显示层去重遮掩双写”，切卡/重载即失效。
- **滚动**：`scheduleScrollTimelineToBottom`（L571-584）双 rAF + 200ms timer，每次 `timelineItems.length` 变化（L612）即滚底。无 `stick-to-bottom` 判断（仅 `jumpLockUntil` L563），用户上翻看历史时仍被拽底；无 “N 条新消息” pill。
- **遥测口径混乱**：组级 `telemetry` 取自 `msg.inputTokens`（`turnGroup L255`），活轮取自 `agentStore.telemetry`（L152-161），`budgetStatus.protocol` 又参与 `protocolOfGroup`（L456），三处口径不同，`IN` 快照语义用户看不懂（title L101 强行解释）。

### 2.2 `MarkdownStream.vue`（84 行，流式性能主犯）

- `rendered = computed(() => md.render(tolerantMarkdown(text)))`（L66）：**每 token 全量 `md.render`**，复杂度 `O(全文)`。千 token 回答流式期触发上百次全量解析 + `highlightAuto`（L45，自动语言检测，最贵）逐代码块重跑。`highlightAuto` 对半截代码会误判语言导致闪烁，且不可缓存（无 `key=lang+hash` 缓存）。
- 容错仅补未闭合 ` ``` `（L62），表格未闭合、数学公式未闭合、链接半截均无处理，半截表格会整段消失一帧。
- 无 rAF 节流、无 `requestIdleCallback` 终排、无 Web Worker 选项。`v-html` 全量替换导致 DOM 全量重建，光标/选区/图片闪烁。

### 2.3 `ToolCallCard.vue`（528 行，次犯）

- `parseArgs()`（L318）每次渲染 `JSON.parse(argsJson)`，`diffLines`（L352）每次全量 `split('\n')`，`receivedBytes` 变化（流式字节计数 L289）触发整卡重渲染 → diff 重算。无 `computed` 缓存分层（应拆 `HeaderMemo` + `BodyLazy`）。
- 流式输入不可见：P1-F2 后 `ToolCallUpdated/Args` 不再拼 `argsJson`（`agentStore L466-475` 只标脏），`refreshFromProjection` 又只在 `projection:applied` 时对账，而投影 `inputText delta` 对文件类工具 100ms 节流 + `replayable` 档不发 delta（`StreamToRowProjector L206-223`）→ 流式期卡面 `argsJson=''`，`summaryText` 回退空，`diff` 空，用户看到“执行中”空卡。
- `displayStatus`（L228）兼容 10 种字符串，但上游 `cardStatusOfRowState`（`agentStore L244`）把 `cancelled/interrupted` 映射为 `done`，取消态显示“已完成”，语义错误。
- 重型内容 `heavyVisible`（L242，`rootMargin 240px`）方向正确，但 `diff` 占位（L109）与图片占位共用同一 `heavyVisible`，且 `showAllDiff` 15 行截断写死，无“按文件/按 hunk 折叠”。
- `isSpawn` 的 `subId` 用正则从 `displayOutput` 文本里抠 `subSessionId`（L501-508），脆弱；应读行 `extra/subSessionId` 结构化字段。

### 2.4 `toolCallRowToCard.ts`（221 行，桥接层已腐一半）

- `resolveRenderer`（L51）按家族映射正确，但 `MessageTimeline` 调用点（L307）对每 `toolMessage` 都 `toCard()` 两次（`isFallbackTool` + `fallbackToolName`/`fallbackRawJson`），每 `toCard` 又 `find` 全量 `persistedMessages`（L272），`O(工具数×消息数)`。
- `toCardFromMessages`（L129）从 `assistant.toolCalls[].function.arguments` 回填参数，但多 iteration 同 `callId` 复用/`toolCallId` 缺失时 `find` 错位；`status` 只看 `[Tool Error` 文本嗅探（L146），与投影 `toolStatus` 权威相悖。
- `toolRowToCard`（L172，新行转卡）已写但**无调用方**（死代码），说明 P2 桥接写完未接线。

### 2.5 `agentStore.ts`（918 行，状态机臃肿）

- 三类状态混存：流式文本（`streamingText/Reasoning` 字符串 `+=` L381/387）、工具卡（`toolCards[]` L446）、遥测（`telemetry` L390）。字符串 `+=` 每次触发 Vue 深层响应式 + 下游全量 `computed`（`hasActiveTurn` L232、`hiddenToolCallIds` L238 新 `Set` 每次重建）。
- `refreshFromProjection`（L295）单向对账只修正 `argsJson/状态/字节`，不删除幽灵卡、不处理 `row.removed`，双写漂移只遮不治。
- `finishTurn`（L686）轮末 `loadSessionMessages` 全量重拉（`refreshAfterTool L679`），长会话每轮一次全量 `messages.jsonl` 解析 + `snapshotFromMessages` 重建，输入法卡顿主因之一。
- `estTokens/liveEst`（L50/382）在渲染 store 里做 token 估算，每 delta 一次 `for..of codePoint` 循环，热路径浪费。

### 2.6 `projectionStore.ts`（918 行，底子好但被架空）

- `applyDelta/coalesceDeltas`（L174/243）与 C# `ConversationDeltaApplier` 逐条对应正确，`onSnapshot/onFrame/mergeRange/pushOptimistic` 三规则正确，`shallowRowEqual` 引用共享（L896）正确。**问题不在实现，在接线**：`workspaceStore.loadSessionMessages`（L428）走 `snapshotFromMessages` 本地重建而非后端 `Snapshot()` 直供快照，导致 `seq/subscriptionId/confirmedCommands` 全假（`snapshotFromMessages L480-487` 写死 `seq=prev.seq`），`onFrame` 永无真帧可消费，`coalesce` 无用武之地。
- `snapshotFromMessages` 的 `rowIdSeed`（L369）模块级自增 → 每次重载 `rowId` 全变 → `v-memo`、`data-row-id` 锚点、`useTimelineNav` 顺序全失效；`rowsToMessages`（L491）又把行转回消息供旧渲染，形成“行→消息→组→行”绕圈。
- `syncPendingMirror` 写 `window.__projectionPendingInteractions`（L752）全局变量供 `ToolCallCard` 读取，属于跨 store 暗道，应改为 `pendingOf(sessionId)` 显式注入。

### 2.7 `turnGroup.ts` + `useTimelineGroups.ts`

- 四纪律（header 权威/空 reasoning 过滤/`EnterPlanMode` 过滤/轮尾摘出）方向正确，但 `headerStates/runningTurnIds/isRunningWork` 全是可选注入（L84-91），实际调用方（`MessageTimeline L235`）一个不传 → `isRunning` 恒 `false`（L209），活轮判断回退到 `agentStore.hasActiveTurn`，持久与流式两套 `running` 口径。
- `markerKindOf`（L68）靠 `rowKind/markerKind/name` 三处猜，`mergeKeyOf`（L124）图片指纹正确但无调用方。`exportSessionMarkdown`（L334）与渲染无关却塞在组装文件，应搬走。
