# 00 总览：双协议兼容与前端渲染全链路地图

> 适用读者：要把“同时兼容两种模型协议 + 流式正确渲染文本与工具调用”的设计搬到别的项目的人。
> 本文只讲全貌与数据流向，细节分别在 01~07 篇展开。所有代码均为为学习重写的示意代码，不依赖任何仓库。

## 1. 一句话结论

所谓“同时兼容 response 协议和 chat 协议”，本质是：

- 对外暴露一套与协议无关的模型接口：`generateText / streamText`，输入是统一的 `ModelInputMessage[] + ModelToolContract[]`，输出是统一的 `ModelStreamEvent` 流。
- 在内部用一个**分发层**按 provider 配置的 `apiType` 选择不同的底层 SDK 工厂：
  - `apiType = anthropic-messages` 走 Anthropic 风格工厂；
  - `apiType = openai-responses` 走 OpenAI Responses 风格工厂；
  - `apiType = openai-chat-completions` 走 OpenAI Chat Completions 兼容风格工厂。
- 分发之后的所有链路（流式归一、业务投影、增量下发、前端渲染）只认统一事件，不再感知底层是哪个协议。

这就是“一次分发，处处统一”。

## 2. 三种协议到底差在哪

初学者容易把它们当成完全不同的东西，其实差异集中在三处：

| 维度 | Chat Completions 风格 | Responses 风格 | Anthropic Messages 风格 |
|---|---|---|---|
| 请求形态 | `messages[] + tools[]`，多轮 system 需合并 | `messages[] + tools[]`，但 reasoning 有服务端存储引用 | `messages[] + tools[]`，system 可多条（为缓存保留） |
| 流式增量 | `choice.delta.content / tool_calls[].function.arguments` 碎片 | `output_text.delta / function_call_arguments.delta` 等碎片，外加 `response.id / item.id` 身份 | `content_block_start/delta/stop`，thinking 有签名 |
| 工具终态 | 靠拼接 arguments JSON 得到完整调用 | 靠完整 `function_call` 项得到完整调用，需补 `message.id / annotations` 兼容 | 靠完整 `tool_use` 块得到完整调用 |

如果每一层都 `if (protocol === ...)`，代码会迅速腐烂。正确做法是把差异收敛到两个边界：

1. **请求投影边界**：把统一消息翻译成各 SDK 要的形态；
2. **流式归一边界**：把各 SDK 的碎片翻译成统一的流事件。

## 3. 全链路一图流

```text
用户输入
  |
  v
统一模型请求 { messages, tools, toolChoice, temperature, ... }
  |
  v
[分发层] 按 apiType 选 SDK 工厂 + 组装 fetch 洋葱
  |  openai-responses -> Responses 工厂
  |  openai-chat-completions -> Chat 兼容工厂
  |  anthropic-messages -> Anthropic 工厂
  v
[请求投影层] 统一消息 -> SDK 消息 / 统一工具 -> SDK 工具
  |
  v
底层 SDK 发起 HTTP/SSE，返回厂商碎片流
  |
  v
[流式归一层] 厂商碎片 -> ModelStreamEvent {
    start, text_start/delta/end,
    reasoning_start/delta/end,
    tool_input_start/delta/end, tool_call,
    finish{finishReason, usage}, error
  }
  |
  v
[业务投影层] ModelStreamEvent -> 行级增量 {
    row.appended(新行) / row.delta(文本追加) / row.upserted(整行替换)
  }
  |
  v
[增量通道层] 合并相邻 delta，保证“合并后终态 == 逐条投递终态”
  |
  v
[前端投影存储] snapshot 整体替换 + 按序 apply delta，断档重订阅
  |
  v
[轮次组装层] 按 turnId 把平铺行组成“用户输入 + 工作区(正文/工具/思考)”
  |
  v
[行渲染层]
  - assistantText 行 -> Markdown 流式渲染
  - reasoning 行 -> 可折叠思考块
  - toolCall 行 -> 按工具家族选卡片渲染
```

## 4. 为什么文本和 toolCall 是两条渲染路径

- 文本是**追加语义**：`row.delta(path=text, append="...")` 不断拼字符串，前端只需把字符串做 Markdown 渲染，流式对未闭合代码块容错即可。
- 工具是**状态机语义**：`inputStreaming -> pendingApproval/running -> success/error/cancelled`，外加 `inputText` 流式预览、`input` 定稿、`output.text` 结果、`progress` 进度、`display` 结构化载荷。前端必须先把行桥接成旧卡片模型，再按工具名选 renderer。

两者共用“行”容器，但数据字段、更新操作、渲染组件完全不同。混在一起写是新手最常见的错误。

## 6. 设计口诀（可直接抄到新项目）

```text
1. 对外只暴露一种消息模型、一种流事件模型。
2. 协议差异只允许出现在两个函数里：buildSdkRequest() 与 normalizeSdkChunk()。
3. 工具输入只信任终态完整调用，不从展示用 delta 猜测。
4. 结构变化用整行替换，文本增长用追加，不做字段级 patch。
5. 快照整体替换，增量按序应用，断档不猜直接重订阅。
6. UI 不推导业务状态，所有“是否可见/是否运行”由投影下发。
```
