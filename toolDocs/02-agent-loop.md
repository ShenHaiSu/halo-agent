# 02 Agent 循环与工具执行调度

> 本篇讲模型一次回复里的多个工具调用如何被执行：何时串行、何时并行、如何校验、如何拦截、如何收尾。复现时照此实现循环即可兼容多工具模型。

## 2.1 循环总览

一次用户提问触发一轮循环，循环分内外两层：

- 内层：反复请求模型、执行工具调用，直到模型不再调工具或被要求停止。内层处理排队中的追问。
- 外层：模型想停时看是否有后续跟进消息，有则继续，无则结束。

每轮请求前做三件事：准备下一轮上下文、声明工具差异、转换消息为模型可读格式。每轮请求后做两件事：流式收模型回复、执行其中的工具调用。

## 2.2 请求前：声明工具差异

可执行集与历史声明可能不一致，如用户中途开关工具。每次请求前对比两者，差异写成系统消息补丁：

- 新增的工具进新增列表，删除或改定义的工具进删除列表。改定义视为先删后加。
- 若已有待发送的系统消息，则将其工具字段替换为差异；否则在首条非系统消息前插入一条空系统消息承载差异。
- 无差异则不插入，避免污染上下文。

历史声明按序重放：后一条系统消息的增删覆盖前一条，最终得到当前声明。请求时按传输能力二选一：支持锚定的传输把初始工具放请求头、增量放系统消息处；否则直接发当前全量。

## 2.3 回复截断保护

若模型回复因输出 token 上限被截断，其中的所有工具调用一律不执行，直接逐个生成失败结果，文案大意是调用未执行，参数可能被截断，请用完整参数重发。因为流式参数用尽力 JSON 修复，截断参数可能恰好能过校验但语义不全，执行会有风险。

## 2.4 执行模式：串行与并行

全局有两种模式，默认并行，单个工具可用并发模式覆盖：

- 串行：逐个经历准备、执行、收尾，前一个落盘后再跑下一个。顺序与模型原文顺序一致，结果消息也按原文顺序。
- 并行：先逐个串行做准备，凡准备通过的并发执行。结束事件按完成顺序发，结果消息仍按原文顺序拼，保证上下文稳定。

若同批任一调用的工具标为必须串行，则整批降级为串行。文件写工具虽未强制标串行，但靠文件串行队列实现同文件串行、异文件并行，效果等价。

事件顺序：每调用先发开始事件，执行中有增量事件，执行完发结束事件，结果消息事件在后。界面靠开始与增量画进度，靠结束画耗时，靠结果消息回放。

## 2.5 单调用四步：准备、执行、收尾、落盘

### 准备

1. 按名找可执行工具，找不到则直接生成失败结果，文案为工具不存在。
2. 跑参数预处理垫片，把畸形修成标准形。
3. 按参数结构校验，失败则生成失败结果，文案含字段路径与收到的参数原文。
4. 跑前置钩子，返回阻止则生成失败结果，文案用钩子给的原因或默认被阻止文案，并记录终止建议。

准备失败的调用不进执行函数，不计时，不占并发槽。

### 执行

调用执行函数，传入调用编号、已校验参数、中止信号、增量回调、扩展上下文。计时从进入执行函数起，到返回或抛异常止，用单调时钟。若抛异常，转为失败结果，文案为异常消息，细节尽量保留。若中止信号触发，命令与搜索走杀进程或关流，文件写走轮询检查，统一转为操作已中止。

### 收尾

跑后置钩子，按字段覆盖结果。内容覆盖则全量替换内容数组，细节覆盖则全量替换细节，失败标记、用量、终止建议同理。内容给了但结构化内容没给，则丢弃旧结构化内容，防止文不对题。

### 落盘

把终态拼成工具结果消息，含调用编号、工具名、内容、是否失败。串行按执行顺序落盘，并行按原文顺序落盘。落盘后计入上下文，供下一轮模型可见。

## 2.6 提前结束规则

每批执行完看终止建议：仅当批内每个终态都建议终止时才停，否则继续请求模型。这防止单个工具误停。被前置钩子阻止的调用也可带终止建议，参与投票。全局完成钩子还可强制结束或强制继续，优先级高于投票。

## 2.7 中止与排队

- 用户中途输入进转向队列，当前模型回合结束后注入；模型想停后的输入进跟进队列，停稳后注入。两种队列各有全放行与每次放一条两种模式。
- 中止信号取消当前请求与执行，串行循环遇中止即跳出，并行对未起跑的直接生成操作已中止。
- 重置时保留基线提示与工具基线，清消息、清队列、清进行中的调用标记。

## 2.8 复现要点

- 先实现串行版：准备、执行、收尾、落盘、声明差异、截断保护，即可跑通。
- 再加并行：准备串行、执行并发、结果按原文排序、结束事件按完成排序。
- 前置与后置钩子、终止投票、中止、排队是生产必备，不要省略。
- 所有失败必须落成工具结果消息回给模型，不要只记日志，否则模型会一直重试。
