# Tailwind 自定义色 `var()` 纯字符串：`/40` 透明度修饰静默失效，边框落到 preflight 兜底浅灰

- 状态：**已闭环**（2026-11-15 修复 + 静态守卫落地）
- 日期：2026-11-15
- 环境：Win10 x64 / WebView2(Chromium 109 约束) / Node 22 / Vue 3.5.43 / Tailwind 3.4.19
- 现象：
  暗黑主题下，**会话列表中"当前激活会话"的边框**、以及**顶栏上下文预算监控悬停卡里"指标详情"那一圈边框**，
  表现为一条亮灰白边框糊在深色背景上，不像暗色主题该有的 `#283241` 近黑蓝；
  同时这两个元素也**丢掉了本该有的主题蓝（accent）强调**。切到明亮主题时看起来"基本都正确"。
- 复现步骤：
  1. 明亮主题下观察侧边栏会话列表激活项、顶栏 ··· 上下文预算监控悬停卡 → 视觉正常。
  2. 切到暗黑主题（顶栏 ☀/🌙 按钮），同样两处 → 出现刺眼的浅灰边框，且没有蓝色强调。
- 根因：
  `tailwind.config.js` 把语义色定义成**纯 `var()` 字符串**，没有 `<alpha-value>` 占位符：

  ```js
  colors: {
    app: 'var(--bg-app)',        surface: 'var(--bg-surface)',
    subtle: 'var(--border-subtle)', accent: 'var(--accent-primary)', /* ... */
  }
  ```

  Tailwind v3 处理颜色透明度修饰走 `withAlphaValue()` → `parseColor(color, {loose:true})`。
  `var(--x)` **不是** hex/rgb()/hsl()/color()，`parseColor` 返回 `null`，
  于是 `withAlphaValue(..., defaultValue=undefined)` 返回 `undefined`
  → 声明被丢弃 → 整个规则为空 → 被裁剪。
  **结论：任何 `<utility>-<自定义色>/<数值>` 的类一个 CSS 规则都不生成。**

  实测（`npx tailwindcss --content` 单类探针）：

  ```
  border-accent/40  border-subtle/50  bg-surface/60
  → warn - No utility classes were detected in your source files.
  ```

  编译产物中 `.border-accent{...}`、`.border-subtle{...}` 存在，但
  `.border-accent\/40`、`.border-subtle\/50`、`.bg-surface\/60` **完全缺席**
  （对照：`.text-amber-500/50` 正常，因为 `amber-500` 是可解析的 hex）。

  为什么"亮色看着正常、暗色不正常"——Tailwind preflight 给所有元素兜底：

  ```css
  *, ::before, ::after { border-color: #e5e7eb; }  /* gray-200 浅灰 */
  ```

  所以 `border` + `border-accent/40` 的元素边框色从未被设置，落到 `#e5e7eb`：

  | | 本该是 | 实际渲染 | 观感 |
  |---|---|---|---|
  | 亮色 `--border-subtle` | `#e2e8f0` | `#e5e7eb` | 几乎一致 → 看不出问题 |
  | 暗色 `--border-subtle` | `#283241` | `#e5e7eb` | 亮灰白边框 → 违和 |

  这就是"亮色正确、暗色不遵守主题"的全部原因：**不是主题变量没切，而是这条边框根本没吃到变量。**

- 解法（**已按方案 A 落地**，方案 B 未采用）：
  - **方案 A（根治，已采用）**：给 8 个语义色各补一份 RGB 三元组变量，config 改用 `<alpha-value>`。
    约束：`main.css` 注明 Chrome 109 安全（不可用 `color-mix`，Chrome 111+），
    `rgb(R G B / a)` 空格分隔写法 Chrome 65+ 即可，满足要求。

    ```css
    :root{ --bg-app-rgb: 13 17 23; --bg-surface-rgb: 24 31 41;
           --bg-elevated-rgb: 33 42 54; --border-subtle-rgb: 40 50 65;
           --text-primary-rgb: 230 237 243; --text-secondary-rgb: 139 148 158;
           --accent-primary-rgb: 59 130 246; --bg-sidebar-rgb: 19 24 32; }
    html.light{ --bg-app-rgb: 248 250 252; --bg-surface-rgb: 255 255 255;
                --bg-elevated-rgb: 248 250 252; --border-subtle-rgb: 226 232 240;
                --text-primary-rgb: 15 23 42; --text-secondary-rgb: 100 116 139;
                --accent-primary-rgb: 37 99 235; --bg-sidebar-rgb: 241 245 249; }
    ```

    ```js
    colors: { subtle: 'rgb(var(--border-subtle-rgb) / <alpha-value>)', /* ... */ }
    ```

    **额外必改一点**：`stores/appearanceStore.ts:67` 会在运行时 `setProperty('--accent-primary', s.themeColor)`
    （用户可自定义主题色）。若不**同步**写 `--accent-primary-rgb`，自定义主题色会把 accent 系列打回默认值。
    需要在 `applyToDom()` 里把 hex 拆成 `R G B` 一并 set（并把 `text-error`/`text-success` 补进 config）。
    保留原 hex 变量不动 → 组件内既有 `var(--border-subtle)` 等内联写法零风险、全部一次性修好。
  - **方案 B（最小改动）**：只给出问题处新增 `--border-accent-soft` / `--border-subtle-50` 之类的
    显式 rgba 变量（`:root` + `html.light` 双份），把 `/40` `/50` `/60` 换成 `border-[var(--xxx)]`。
    改动面小，但坑还在——以后写 `/xx` 继续静默失效。

- 教训（下次如何避开）：
  1. **自定义色只要打算用透明度修饰，就必须是 `rgb(var(--x-rgb) / <alpha-value>)` 或 `--x: 24 31 41` + `rgb(var(--x) / <alpha-value>)` 形式**；
     纯 `var(--hex)` 只适用于不带 `/数值` 的场景。
  2. 这类失效**不报错、不告警**（单类探针时才出 "No utility classes were detected"），
     唯一可靠的检查手段是**看编译产物里有没有对应类**，或在暗色主题下肉眼验。
     已用 `scripts/assert-tailwind-color-alpha.mjs` 在 build 前静态拦截（见上「静态守卫用法」）。
  3. 排查"某处不跟随主题"时，先怀疑**样式没吃到变量**，再怀疑主题变量没切换。
     打开 devtools 看该元素 computed `border-color` 是不是 `rgb(229, 231, 235)` —— 那就是 preflight 兜底的指纹。
  4. 同理：写了 `bg-error` / `text-success` 之类却没用，多半是 token 压根没在 `theme.extend.colors` 里定义。
  5. 「配置 + CSS 变量 + 运行时同步」是一个整体：只改 config 会让自定义主题色打回默认蓝，
     只改 CSS 会让类不生成 —— 三者必须同一提交落地。
