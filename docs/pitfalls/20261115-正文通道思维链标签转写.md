# 思维链写在 `content` 正文里的提供商：正文被 `<think>` 污染，全链落盘带标签

- 状态：**已闭环**（2026-11-15 网关解析层加流式标签提取器 + 开关）
- 日期：2026-11-15
- 环境：Win10 x64 / .NET 6.0.428 / xUnit（后端单测）
- 现象：
  某提供商 chat 模型把思维链塞在正文通道：`delta.content` 以 `<think>` 开头、`</think>` 收尾，
  中间还可能穿插 `tool_calls` 增量（工具仍能正常调用）。表现为：
  1. 「过程」折叠栏**不出现**思考文本，思维链全部混在正文气泡里，并带着 `<think>` / `</think>` 字面量；
  2. 落盘 `Assistant.Content` 含标签、`Assistant.ReasoningContent` 为空；
  3. 下一轮把带标签的正文原样回发（`content` 通道），模型被自己的标签污染上下文。
- 复现步骤：
  1. 配一个把思维链写进 `content` 的模型，随便问一句话 → 正文出现 `<think>…</think>`；
  2. 让它调一次工具（如 `exec_command`）→ 工具卡正常，但思维链仍留在正文里；
  3. 查看会话落盘（`messages.jsonl` 末条）→ `content` 含标签、`reasoningContent` 为空。
- 根因：
  Chat 适配器只认两个**专用字段**（`delta.reasoning_content` / `delta.reasoning`）作为思考增量，
  `delta.content` 无条件原样发 `TextDelta`；`tool_calls` 是独立分支、根本不看 `content`。
  于是"标签内文本进正文 + 工具照常"是必然结果：**缺的不是开关，而是 content 通道内的流式标签提取器**。
  下游（`LlmCaller` 的 `textAcc/reasoningAcc` 二分累加、`TimelineBlockTracker` 按 kind 切块、
  `HistoryAppender` 落 `Content/ReasoningContent` 双字段、前端 `ReasoningDelta` 渲染）**早已就绪**，
  它们只消费事件 kind，不解析正文内容。
- 解法（最小改动）：
  1. 新增纯函数状态机 `ThinkTagStreamFilter`：吃 `content` 增量、吐有序 `(IsReasoning, Text)` 段。
     关键点：
     - **只扫 content**：`reasoning_content / reasoning` 是专用字段，`tool_calls[].function.arguments`
       里出现同名标签是合法 JSON 字符串，喂进去会把工具参数吃成思维链；
     - **跨包残尾**：分块边界可能切在标签中间（如尾包 `<thi` + `nk>`），保留"疑似标签前缀"至多 7 字符
       （闭标签 8 字符，上界即 7），下包拼接后再判定；流结束时残尾按当前归属补发，因此**截断在标签中间不丢字节**；
     - **未闭合按思维链算**：`finish_reason=length` 截断时思维链不该被当正文丢掉；
     - **per-stream 实例**：标签状态与残尾是流内状态，静态共享会让并发流串味。
  2. 适配器只在 `content` 分支处接一次（`§3.2`），把一段 `Text` 拆成 `Reasoning* + Text*`，
     `[DONE]` 与 EOF 两处出口补 `FlushEnd()`；`reasoning_content` 分支与 `tool_calls` 分支一行没动。
  3. 开关落在模型配置（`Auto` 默认 / `Off` 回退 / `On` 显式声明），**按请求作参数传给适配器**——
     适配器是网关单例，模式存实例字段会在并发流之间串味（这条是最容易踩的设计陷阱）。
     手工映射的存储归一化（`NormalizeModelForStorage`）也必须补一行，否则界面上保存一次就会被重置成默认值。
  4. 下游零改动：前端渲染、桥合并、时间线落盘、历史回发全部复用既有 `ReasoningDelta / TextDelta`。
- 关联提交 / PR：本次提交（新增 `ThinkTagStreamFilter`、适配器分流、模型开关；`ThinkTagStreamFilterTests` 21 项）
- 教训（下次如何避开）：
  1. **先确认"是缺能力还是缺开关"**：当上游把某类内容放在错误的字段里时，开关只能关掉功能，
     真正需要的是在**协议解析层**做一次 kind 转写；放到聚合层（如 `LlmCaller`）做字符串二次扫描会破坏流式时序与工具穿插。
  2. **流式状态机的验收必须锁死"无标签零抖动"**：这是防止转写把普通模型带偏的唯一契约，
     用既有三通道并行用例（reasoning / content / tool_calls）原样回归一遍即可证明。
  3. **单例服务 + 每请求配置 = 竞态**：任何"每请求不同的行为"都不要存进单例字段，走方法参数。
  4. **手工字段映射是隐形坑**：`Clone()`、存储归一化、预览映射这类逐字段拷贝，新增配置项时逐个补齐，
     漏一处的症状是"设置后没生效/保存后被重置"，且不会报错。
  5. **标签口径要显式锁定**：V1 只认全小写精确 `<think>` / `</think>`，大小写变体与 `<think x>` 一律当普通文本，
     并用用例固定——否则模糊匹配会在"教用户写标签"这类正常问答里误伤。
